# Task System

_Status: active design notes — part of the initial architecture session_

Related: `architecture-overview.md`, `knowledge-acquisition.md`, `prompting-system.md`, `database-schema.md`

---

## The Problem

A language learning platform needs many different kinds of exercises — comprehension
questions, fill-in-the-blank, translation, listening tasks, production tasks,
transcription, scanning handwritten answers. These task types will grow over time.
Different languages need different task types. Audio support adds more. Scan/print
adds more.

The naive solution — a big switch statement and per-type columns in the database —
collapses immediately when you add the third or fourth type. The system needs to be
designed so that adding a new task type requires writing one new thing, not
modifying five existing things.

---

## The Core Insight: Separate the Invariant from the Variable

Every task, regardless of type, shares the same lifecycle:

```
generated → presented to user → response collected → graded → signals updated
```

What varies between task types is:
- What the task content looks like (the question, the prompt, the audio clip)
- What a valid response looks like
- How grading works (rule-based vs. LLM)
- Which knowledge items it exercises
- Whether it makes sense for a given language

The database schema captures the invariant lifecycle. The task type plugin captures
everything variable.

---

## The TaskType Interface

Each task type is a Go struct implementing a single interface registered at startup.
The interface is the contract. The registry is the lookup table.

A TaskType must answer:

- **What am I?** — a stable string ID (e.g. `"comprehension_mc"`, `"fill_blank"`,
  `"listen_transcribe"`) and which languages it supports (empty = all languages)
- **How do I generate content?** — given a story, a learner context, and selected
  target items, produce a JSON blob that fully describes the task content (the
  question, options, audio reference, whatever the type needs)
- **How do I grade a response?** — given the content JSON and a response JSON,
  produce a grade. Some types can grade by rule (exact match, regex, set
  membership). Others need the LLM. The interface declares which via `NeedsLLM()`.
- **What items do I target?** — given the content JSON, return the knowledge item
  IDs that this task is practicing. This is how task performance flows back into
  `user_knowledge`.

What a TaskType does NOT own:
- Database access (the handler does that)
- HTTP concerns
- Auth
- Session management

The task type is pure domain logic. It knows about stories, items, and language.
It knows nothing about HTTP or storage.

---

## The Task Registry

At server startup, each task type calls `registry.Register(myType)`. The registry
is a map from type ID to TaskType implementation.

When a request comes in to generate tasks for a session, the handler asks the
language plugin which task type IDs are appropriate for this language and level,
then asks the registry to look each one up, then calls `Generate()` on each.

When a response is submitted, the handler looks up the task's type ID, retrieves
the TaskType from the registry, and calls `Grade()`.

Adding a new task type is:
1. Write the new Go file implementing the interface
2. Call `registry.Register()` in main
3. Declare it supported in the relevant language plugin(s)

Nothing else changes. Existing task types are not touched.

## Database Schema

The key decision: task content, responses, and grades are all stored as JSON blobs.
The base table captures the invariant lifecycle. Type-specific data lives in JSON.
The database never knows what a task looks like — only the task type plugin knows.

```
tasks
    task_id         TEXT  PRIMARY KEY
    session_id      TEXT  NOT NULL      -- which session this belongs to
    user_id         TEXT  NOT NULL
    language        TEXT  NOT NULL
    task_type       TEXT  NOT NULL      -- registered TaskType ID
    content         JSON  NOT NULL      -- generated by TaskType.Generate()
    response        JSON               -- submitted by user; null until answered
    input_method    TEXT               -- 'typed' | 'scanned_image' | 'audio_recording'
    media_path      TEXT               -- path to image or audio file if applicable
    grade           JSON               -- produced by TaskType.Grade(); null until graded
    graded_at       REAL
    created_at      REAL  NOT NULL

task_targets
    task_id         TEXT  NOT NULL
    item_id         TEXT  NOT NULL      -- knowledge_items.item_id
    PRIMARY KEY (task_id, item_id)
```

The `task_targets` table is populated from `TaskType.Targets(content)` immediately
after generation. This is what lets task performance update the right rows in
`user_knowledge` — the signal flows through `task_targets`.

The `input_method` field is set at response submission time, not generation time.
The same task can receive a typed response or a scanned image — the task type
handles both via the same `Grade()` interface. If `input_method` is
`'scanned_image'`, the grader first runs OCR on the image at `media_path` to
extract text, then grades that text as if it were typed. The task type does not
need to know about scanning.

## Session Model

Tasks don't float free — they are always grouped into a session. A session is a
single study unit: one generated story plus all the tasks derived from it.

```
sessions
    session_id      TEXT  PRIMARY KEY
    user_id         TEXT  NOT NULL
    story_id        TEXT  NOT NULL
    language        TEXT  NOT NULL
    created_at      REAL  NOT NULL
    completed_at    REAL               -- null until all tasks done or user exits
```

The session is the unit of progress reporting. "You completed 3 of 5 tasks in
this session" is a session-level query. "Your overall progress this week" is an
aggregation over sessions.

Sessions also drive the adaptive loop: after a session completes, the signal
aggregation step reads all task_targets for the session's tasks, updates
user_knowledge accordingly, and recomputes acquisition stages. The next session's
selection layer sees the updated knowledge state.

## Grading: Rule-Based vs. LLM

Not all grading needs the LLM. Spending LLM tokens to grade a multiple-choice
question is wasteful. The interface declares this cleanly via `NeedsLLM()`.

**Rule-based grading** (fast, free, deterministic):
- Multiple choice: is the response one of the correct option IDs?
- Fill-in-the-blank with a fixed expected answer: exact match after normalization
- True/false
- Ordering tasks: is the sequence correct?

**LLM grading** (slow, costs tokens, needed for open-ended):
- Free-text translation: is the meaning conveyed? Is the grammar acceptable?
- Production tasks: write a sentence using construction X — did they use it correctly?
- Listening transcription: does the transcript match the audio well enough?
- Spoken response: (future) was the pronunciation and content acceptable?

The LLM grader receives the task content, the expected target items, and the
user's response. It returns a structured grade JSON that includes: whether the
item was used correctly, what constructions were demonstrated, what errors were
made. This structured output flows back into `user_knowledge` via `task_targets`.

One important nuance: LLM grading is not binary. A user who wrote `ἔπεσεν`
when the target construction called for a different form may have still
demonstrated understanding of the underlying concept. The grade JSON captures
this — `demonstrated_concept: true, surface_correct: false` — and the signal
aggregation can be nuanced accordingly.

## Language-Specific Task Types

Some task types only make sense for certain languages. The language plugin
declares which task type IDs it supports. The task generation step filters by
this.

Examples of language-specific constraints:
- Greek: genitive absolute identification tasks make sense; tonal distinction
  tasks do not
- Chinese: tonal distinction tasks make sense; genitive absolute tasks do not
- Arabic: root pattern recognition tasks (identify the trilateral root in this
  word); not relevant to non-Semitic languages

A task type can declare `Languages() []string` returning an empty slice to mean
"I work for all languages" (e.g. basic comprehension, true/false). Or it returns
a list of specific language codes it supports.

This means the task type catalogue grows heterogeneously — some types are
universal, some are Greek-only, some are Semitic-only. The registry handles this
transparently. The handler never hard-codes which types go with which language.

## Input Modalities as Task Properties

The task system is designed to treat input method as a property of the response,
not of the task type. This is a deliberate choice.

A fill-in-the-blank task can be:
- Answered by typing in a web form (default)
- Answered on paper and scanned back in
- Answered by speaking (future)

The same task type handles all of these via the same `Grade()` interface. The
pre-processing layer (OCR for scan, STT for audio) extracts a text response and
passes it to the grader as if it were typed. The task type implementation never
sees the raw image or audio.

This keeps task types simple and lets input modalities evolve independently. A new
input method (e.g. handwriting recognition that preserves character-level data
instead of just text) does not require rewriting every task type.

### Print Mode

Any task can be rendered for printing. The task type optionally implements a
`PrintTemplate()` method that renders its content JSON into a printable HTML
fragment. A print endpoint collects all tasks for a session and renders them into
a single printable page.

Scanned responses are submitted via an image upload endpoint. The server routes
the image through OCR (a vision model call), extracts the response text, and
stores it with `input_method = 'scanned_image'` and `media_path` pointing to the
stored image. Grading proceeds normally from there.

## The Signal Flow: Task → Knowledge

After a task is graded, its results flow back into the knowledge model:

```
grade JSON
    └─ task_targets → knowledge item IDs exercised
    └─ grade.correct / grade.partial / grade.demonstrated_concept
           ↓
    user_knowledge.task_correct += 1  (if correct or demonstrated)
    user_knowledge.task_total   += 1
           ↓
    acquisition_stage recomputed (hard system, no LLM)
           ↓
    knowledge_predictions invalidated for affected items
```

The task system does not directly touch `user_knowledge`. It produces a grade.
A separate signal aggregation step (called after session completion or after each
task submission, depending on latency requirements) reads the grades and updates
knowledge state. This keeps the task system pure: generate, present, grade. The
learning model update is someone else's job.

## Composing Task Sets for a Session

When a session is generated, the task generator receives:
- The story text
- The `SelectedItems` from the selection layer (targets, background, new)
- The language plugin's supported task type list
- The user's current level (beginner/intermediate/advanced)

It then decides which task types to use and how many of each. This decision is
currently rule-based (level determines task type mix) but can evolve toward
being LLM-guided or predictor-guided as the system matures.

The generator calls `TaskType.Generate()` for each chosen type, stores the
resulting content blobs, populates `task_targets`, and returns the session.

The task set for a session is not fixed forever — in principle, additional tasks
can be generated mid-session if the user finishes quickly or requests more
practice on a specific item. The session model supports this; tasks are just rows
attached to a session.

## Open Questions

- Partial credit: the grade JSON supports `demonstrated_concept` but the signal
  aggregation needs a defined formula for how partial credit maps to
  `task_correct` / confidence updates
- Task ordering within a session: is there a pedagogically motivated order
  (e.g. comprehension before production)? Currently unordered.
- Adaptive task generation mid-session: if a user aces the first two tasks, does
  the system generate harder follow-ups? Not yet designed.
- Audio task grading: spoken responses require pronunciation assessment, not just
  content assessment. This needs a specialized grader, possibly a separate model.
